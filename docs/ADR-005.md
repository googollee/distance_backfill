# ADR-005：自动补全后台注册的触发时机与状态管理

## 状态

已采纳

## 背景

参见 [PRD-001](./PRD-001.md) 功能需求7"自动补全开关"、[ADR-001](./ADR-001.md) 方案设计5"触发链路"、[ADR-003](./ADR-003.md)"后台自动补全改为可选开关"、[ADR-004](./ADR-004.md)"并发保护"。

ADR-003 决定了"后台自动补全"要做成可选开关，并列出了需要跟着改动的调用点（`AppDelegate`、`RootView`、`SettingsView`、`PermissionsView`），但只规定了"这些地方都要判断偏好、保持一致"，没有规定**注册/注销具体应该在什么时机触发、由谁负责、如何保证被多次调用时状态依然正确**。代码审查发现，这个空白导致了一个实际问题：`AppDelegate.didFinishLaunchingWithOptions`、`RootView.task`、`PermissionsView`"重新请求授权"按钮，在偏好为开启时都会各自调用 `ObserverRegistrar.registerAndEnableBackgroundDelivery()`，而该方法此前没有任何保护——`ObserverRegistrar` 只用一个 `observerQuery` 变量持有当前查询，重复调用会直接创建新查询并覆盖旧引用，旧查询既不会被 `stop()`，也不再被任何变量持有，导致 `disable()` 只能停掉最后一次注册的查询，前面的查询在本次进程存活期间可能继续触发 `handleUpdate()`——用户在设置页关闭开关后，自动补全在本次运行内仍可能继续生效，与 PRD"操作立即生效"的要求矛盾。

## 两层状态模型

自动补全依赖 HealthKit 的两个独立状态，生命周期完全不同，必须分开理解：

| | `HKObserverQuery` | `enableBackgroundDelivery` |
|---|---|---|
| 作用 | 进程内的订阅，收到匹配数据变化时触发 `updateHandler` | 系统级"资格"，数据变化时允许系统唤醒/新建本 App 进程 |
| 生命周期 | 不跨进程存活，每次新进程都必须重新创建并 `execute()` | 系统持久保存，不会因为进程结束而失效 |
| 每次启动要不要重新处理 | **必须重建**——上次进程里的查询对象已经不存在，不重建这次唤醒就没人接收回调 | **建议重新断言**——HealthKit 没有提供"当前是否已开启"的读接口，重复调用是幂等的，顺带起到自愈作用 |
| 关闭时要不要显式撤销 | 要，`store.stop(query)`，否则本次进程存活期间仍会继续触发 | 要，`store.disableBackgroundDelivery(for:)`，否则系统会在未来继续无意义地唤醒进程 |

两者单独存在都不能达成目标：只开 `enableBackgroundDelivery` 没有存活的查询，唤醒了也没人处理；只有查询在跑但没开 `enableBackgroundDelivery`，App 一旦被系统挂起/终止就再也收不到后续变化。

两个状态目前都由 `ObserverRegistrar` 一个 actor 独占管理（`observerQuery` 私有，外部不可绕过），对外只暴露两个方法：`registerAndEnableBackgroundDelivery()` 同时建立两层状态，`disable()` 同时撤销两层状态。

## 决策

### 1. `registerAndEnableBackgroundDelivery()` 和 `disable()` 都必须能被安全地多次调用

调用方不需要、也不应该自己判断"是不是已经调用过"——由于决策2 里同一个方法会从多个触发点被调用，两个方法各自都要保证：不管被调用几次，最终状态都正确、不产生错误、不产生泄漏的资源。但两者实现这一点的方式不同，不能互相照搬：

**`register` 用短路保护，避免产生孤儿查询：**

```swift
func registerAndEnableBackgroundDelivery() {
    guard HKHealthStore.isHealthDataAvailable() else { return }
    guard observerQuery == nil else { return }   // 已注册就跳过
    ...
}
```

`observerQuery == nil` 在进程内是一个准确的信号——同一个进程里它不可能无缘无故变成非 nil，所以"已建立就整个跳过（包括跳过重新调用 `enableBackgroundDelivery`）"是安全的。这一步是必须的：如果没有这层短路，重复调用会各自创建一个新的 `HKObserverQuery` 并覆盖 `observerQuery`，前一个查询既不会被 `stop()` 也不再被引用，属于真正的正确性问题（孤儿查询、`disable()` 停不干净）。

**`disable` 不能用同一种"提前 return"的方式，因为进程内状态不足以判断是否需要跳过：**

```swift
func disable() async {
    if let observerQuery {
        store.stop(observerQuery)
    }
    observerQuery = nil

    try? await store.disableBackgroundDelivery(for: .workoutType())
}
```

如果给 `disable()` 也加 `guard observerQuery != nil else { return }`，会破坏决策2 里"App 启动时，偏好为假 → 调用 `disable()` 纠偏"这条规则——全新进程里 `observerQuery` 本来就是 nil，不管上一次会话是否真的成功调用过 `disableBackgroundDelivery`。用这个字段短路，会让"纠偏"动作在每次冷启动时都被误判成"已经是关闭状态、不用再做"，而这恰恰是它存在的意义。

`disable()` 现在的写法已经能安全地重复调用，只是不靠短路，而是每一步本身天然幂等：

- `store.stop(observerQuery)` 包在 `if let` 里，`observerQuery` 为 nil 时自然跳过，不会对空值操作，也不会重复 `stop` 同一个查询
- `store.disableBackgroundDelivery(for:)` 每次都会真正发出去，不做跳过——但重复调用这个系统 API 本身是幂等的（已经是关闭状态，再关一次不会报错，系统状态不变），代价只是多一次网络/系统往返，不是正确性问题

两者的区别本质是：`register` 面对的是"重复调用会创建新资源、产生泄漏"的风险，必须靠短路避免；`disable` 面对的是"关闭一个已经关闭的东西"，天然没有这个风险，不需要短路，只需要保证每一步本身对"已经是目标状态"的输入无害。

### 2. 注册/注销只在两类时机触发，不允许第三类

- **App 启动时**：且只能放在 `AppDelegate.didFinishLaunchingWithOptions` 里，这是唯一保证每次进程启动都会执行、包括系统后台唤醒（此时不会渲染任何 SwiftUI View，`RootView.task` 根本不会跑）的钩子。按当前偏好值执行：开着 → `register`；关着 → `disable`。**这一次检查在整个 App 生命周期里只允许发生一次**，不能在 `RootView.task` 里重复做。

- **偏好状态发生变化后**：包括——设置页开关切换（`SettingsView`）；首次询问弹窗被回答（`RootView`，弹窗只在 `!hasPrompted` 时出现，回答后无论选哪个都会同时置位 `hasPrompted = true`）；"重新请求授权"成功后（`PermissionsView`）。新偏好值为真 → `register`；为假 → `disable`。

  "重新请求授权"和"首次授权成功"应该复用同一套后续处理逻辑，而不是各写一份：请求成功后，若 `!hasPrompted` 就弹出"是否开启自动补全"询问（弹窗按钮触发上面的 register/disable）；若已经问过，直接按当前偏好值对齐一次状态（register/disable）——这样"用户之前已经关闭过自动补全，后来因为权限被吊销又重新走一遍授权流程"这种情况，也能在授权成功后被正确地重新对齐，而不会被"只问一次"的规则挡住、又没有任何兜底。

  这两类时机加起来，能覆盖代码里所有需要触发注册/注销的场景，不需要再有第三类判断逻辑。正因为决策1 保证了两个方法本身能被安全地重复调用，这两类时机之间即使在边缘情况下短时间内先后触发（比如启动时的对齐和"重新请求授权"的对齐几乎同时发生），也不会产生错误状态，最多是一次无害的冗余调用。

### 3. `RootView.task` 不再承担"启动检查"的职责

`AppDelegate` 已经覆盖了"App 启动时"这一次检查（见决策2），`RootView.task` 不需要再重复调用 `registerAndEnableBackgroundDelivery()`。它的职责收窄为纯交互流程：请求 HealthKit 授权；成功后按决策2 的规则处理"询问/对齐"。这个简化不会引入回归——`isEnabled` 只有在授权成功过至少一次之后才可能为真，而 HealthKit 授权状态是系统级、跨进程持久的，所以 `AppDelegate` 尝试注册时，授权早已就绪，不存在"注册抢跑在授权前面"的时序问题。

## 已知限制

- 如果用户绕开本 App、直接在系统"健康"App 里撤销了本 App 的读权限，本地偏好 `isEnabled` 不会跟着改变，下次启动 `AppDelegate` 依然会尝试注册，但查询永远不会真正触发。这个状态对 App 不可见，目前只能靠 `PermissionsView` 里的文案提示用户手动去检查，不在这次决策的范围内解决。
- `AppDelegate` 的注册/注销调用是 `Task { await ... }` 包裹的"发射后不管"，不等待结果、也不向用户展示失败信息；这跟此前的实现一致，不是这次决策改变的行为。

## 涉及文件

- `Sources/HealthKit/ObserverRegistrar.swift`：`registerAndEnableBackgroundDelivery()` 短路保护；`disable()` 保持现状（天然幂等，不需要短路）
- `Sources/App/AppDelegate.swift`：偏好为真时 `register`，为假时 `disable`
- `Sources/Views/RootView.swift`：`.task` 去掉重复的 register 调用；首次询问弹窗与"重新请求授权"共用同一套 post-授权处理逻辑
- `Sources/Views/PermissionsView.swift`：`重新请求授权` 改为复用上面的共用逻辑，不再自己写 `if isEnabled { register }`
- `Tests/DistanceBackfillTests/ObserverRegistrarTests.swift`：`testRegisterIsIdempotent` 覆盖决策1 里 `register` 的部分；需要补一条覆盖 `disable` 多次调用仍然正确、以及决策2、3 调用点整合的测试
