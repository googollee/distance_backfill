# ADR-004：并发保护，防止写入重复记录

## 状态

已采纳

## 背景

参见 [PRD-001](./PRD-001.md) 功能需求2"不覆盖、不重复写入"、[ADR-001](./ADR-001.md) 方案设计5"触发链路"、[ADR-002](./ADR-002.md)。用户反馈：会为同一条训练写入两条重复的距离数据。

根因是 `DistanceBackfillService.process()`（`Sources/HealthKit/DistanceBackfillService.swift`）里"判重查询"和"写入"这两步之间隔着一次 `await`，不是原子操作——只要有两次调用几乎同时跑到判重这一步，都会查到"还不存在"，于是各自写了一条。这个竞态有两种触发方式：

1. **`HKObserverQuery` 自身的并发回调**：系统可能针对同一批变更并发调用多次 `updateHandler`，`ObserverRegistrar.handleUpdate()` 的第二次回调可能在第一次还没来得及把新 anchor 存下来之前就触发，两次调用读到同一个旧 anchor、查到同一条新训练
2. **手动扫描与后台自动之间的跨路径并发**：`ScanViewModel`（手动"扫描历史"，跑在 `@MainActor`）和 `ObserverRegistrar`（后台自动，自己的 `actor`）是两个独立的执行上下文，各自持有一份独立的 `DistanceBackfillService` 实例；如果用户手动点"扫描历史"的同时后台自动补全恰好也被触发，两条路径会各自查到"还不存在"、各自写入

两种触发方式的根因相同，都要靠保护 `DistanceBackfillService` 的临界区来解决。

## 决策

### 1. `ObserverRegistrar` 内部去重

把 `ObserverRegistrar` 从普通 `class` 改成 `actor`，加一个 `isHandlingUpdate` 标记位，在 `handleUpdate()` 开头做"检查+设置"：

```swift
func handleUpdate() async {
    guard !isHandlingUpdate else {
        AppLogger.sync.info("已有一次同步在处理中，跳过这次重复触发")
        return
    }
    isHandlingUpdate = true
    defer { isHandlingUpdate = false }
    // ...原有逻辑不变
}
```

用 `actor` 而不是普通 `class + var` 标记：普通 class 里，这个标记位在两个并发 `Task` 中读写本身就是数据竞争（undefined behavior）；`actor` 保证"检查标记、设置标记"这一步天然线程安全，且这个检查+设置发生在第一个 `await` 之前，不会被 actor 的重入（reentrancy）规则打破——即便 `handleUpdate()` 内部后续的 `await` 会让出执行权，第二个并发调用到达时也一定会先看到已经被置为 `true` 的标记，从而直接跳过。

处理策略是**跳过、不排队**：后到的并发调用直接返回，不会等第一个处理完再重新执行一遍。这依赖 `handleUpdate()` 本来就是"处理 anchor 之后的所有新增训练"（不是只处理触发那一刻的单条数据），所以跳过的这次回调不会导致数据丢失——它想处理的训练，会在下一次真正触发的回调里被正常处理到。

这一层解决的是"同一条后台路径被系统连续触发"这种情况，属于提前短路、避免不必要的重复查询，是性能层面的优化，不是防止重复写入的最终防线。

### 2. `DistanceBackfillService` 改为共享 actor + 显式异步锁，覆盖跨路径并发

真正防止"最终写入重复数据"的防线，是把 `DistanceBackfillService` 本身也从 `class` 改成 `actor`，并提供一个进程内共享单例：

```swift
actor DistanceBackfillService {
    static let shared = DistanceBackfillService(recordStore: SwiftDataSyncRecordStore.shared)
    ...
}
```

`ObserverRegistrar` 和 `ScanViewModel` 都改成默认使用这个共享实例，而不是像之前那样各自拿到一个 `recordStore` 就在内部单独构造一份 `DistanceBackfillService`。

但光把类型改成 `actor` 并不够：actor 只保证内部状态的读写不产生数据竞争，对**重入（reentrancy）**不设防——`process()` 内部有多次 `await`（判重查询、写入），两个并发调用一样会在这些挂起点之间交叉执行，都查到"还不存在"、都写入。跟 `ObserverRegistrar` 那层不同，这里不能用"跳过"策略：跳过意味着某条具体的训练可能永远不会被处理，而不是像 `handleUpdate()` 那样下次触发还能兜底捞回来。

所以 `DistanceBackfillService` 内部额外实现了一个显式的异步互斥锁，包住整个 `process()`：

```swift
private var isLocked = false
private var lockWaiters: [CheckedContinuation<Void, Never>] = []

private func acquireLock() async {
    if !isLocked {
        isLocked = true
        return
    }
    await withCheckedContinuation { continuation in
        lockWaiters.append(continuation)
    }
}

private func releaseLock() {
    if lockWaiters.isEmpty {
        isLocked = false
    } else {
        lockWaiters.removeFirst().resume()
    }
}

func process(workout: HKWorkout, using store: HealthStoring) async -> BackfillOutcome {
    await acquireLock()
    defer { releaseLock() }
    // ...原有逻辑不变
}
```

`acquireLock()` 的"检查 `isLocked`、决定是否直接拿到锁"这一步是同步的，发生在第一个 `await` 之前，不会被重入打破；拿不到锁的调用会挂在 `lockWaiters` 队列里，等前一个调用 `releaseLock()` 时被唤醒，按顺序依次执行，而不是被跳过。这样不管调用方是手动扫描还是后台自动，`process()` 的判重+写入临界区任意时刻只有一次真正在跑，其余调用排队等待、最终都会被正常处理到。

为了保留可测试性，`ObserverRegistrar` 和 `ScanViewModel` 的 `init` 都直接接收一个 `backfillService: DistanceBackfillService` 参数（默认 `.shared`），而不是接收 `recordStore:` 再自行构造；测试里各自构造一个基于 `FakeSyncRecordStore` 的独立 `DistanceBackfillService` 实例传入即可，天然跟生产环境的共享单例隔离。

### 连带影响

改成 `actor` 之后，从外部调用非 `async` 方法都需要 `await`／包一层 `Task { await ... }`。涉及的调用点：

- `Sources/App/AppDelegate.swift`
- `Sources/Views/RootView.swift`（两处：`.task` 里、首次询问弹窗"打开"按钮）
- `Sources/Views/SettingsView.swift`（开关打开分支）
- `Sources/Views/PermissionsView.swift`（"重新请求授权"按钮）

`disable()` 本来就已经是 `async` 方法，调用方式不受影响。

## 验证

在 `Tests/DistanceBackfillTests/FakeHealthStore.swift` 里加了一个 `shouldYield` 开关，打开后 `anchoredWorkouts`/`samples`/`save` 这几个关键异步方法会真正调用 `Task.yield()` 让出执行权——不加这个的话，并发的 `Task` 大概率不会真正交叉执行，测试会偶发通过、不可靠，加了之后能确定性地复现竞态。

同时修正了 `FakeHealthStore.save()`：之前保存的对象只会记到 `savedObjects`，不会同步进 `existingSamplesByType`，导致即使调用被正确串行化，第二次调用的判重查询也永远查不到第一次刚写的数据——这会让并发测试即便加了锁保护也一直假性失败。修正后 `save()` 会把 `HKQuantitySample` 同步写入 `existingSamplesByType`，才能真实模拟"保存后能被查到"这个行为。

- `ObserverRegistrarTests.testConcurrentHandleUpdateCallsDoNotWriteDuplicateRecords`：用 `async let` 模拟系统并发触发两次 `updateHandler`，只写入 1 条
- `DistanceBackfillServiceTests.testConcurrentProcessCallsOnSharedInstanceDoNotWriteDuplicates`：直接对同一个 `DistanceBackfillService` 实例并发调用两次 `process()`，验证共享 actor + 锁保护之后同样只写入 1 条（这个测试验证的是"共享 actor + 锁"这个底层机制本身，不经过 `ScanViewModel`/`ObserverRegistrar`）

## 已知限制

- `ObserverRegistrar` 那层"跳过、不排队"的策略意味着，如果并发触发时后到的那次回调恰好带来了第一次回调查询范围之外的更多新数据（理论上不太可能，两次几乎同时发生、查询范围应该高度重合），这部分数据要等到下一次真正触发时才会被处理。这是可接受的权衡：比起排队等待、还要处理"等待期间又来了第三次触发"这类连锁问题，直接跳过更简单，且不会丢数据，只是可能有一次不多的延迟
- `DistanceBackfillService` 改成共享 actor 后，手动扫描和后台自动如果真的同时触发，会互相排队等待，即便两边要处理的是完全不相关的训练也不能同时处理。这是个人使用的健康类工具，训练量级不大，这个代价可以忽略
