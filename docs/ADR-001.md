# ADR-001：基于 HealthKit 的训练距离补全方案设计

## 状态

已采纳

## 背景

参见 [PRD-001](./PRD-001.md)。需要在 iOS 上，将第三方运动 App（如 Zepp）写入健康 App 的训练记录中所携带的距离统计，补写为健康 App 可统计的独立距离数据类型，且不能覆盖/重复已有数据，写入需可追溯、可撤销。

## 关键约束

1. **`HKWorkout` 一旦保存不可变**：无法向别的 App 已写入的训练记录中追加或挂载新的数据。唯一可行方式是写入一条独立的 `HKQuantitySample`，将其 `startDate`/`endDate` 与训练记录的起止时间对齐，通过时间区间关联，而非真正挂载在该条训练记录下。
2. **只能操作自己写入的数据**：无法修改或删除其他 App 写入的数据，删除/撤销只能针对本 App 自己写入的 sample。
3. **训练自带距离统计的读取方式**：通过 `workout.statistics(for: 距离类型)` 取得 `HKStatistics`，其 `sumQuantity()` 即训练详情页展示的那个距离值。这是本方案的数据来源。

## 方案设计

### 1. 运动类型 → 距离类型映射表

维护一份静态配置，将 `HKWorkoutActivityType` 映射到对应的距离 `HKQuantityType`：

| 运动类型（示例） | 距离类型 |
|---|---|
| cycling / handCycling | distanceCycling |
| running / walking / hiking | distanceWalkingRunning |
| swimming | distanceSwimming |
| rowing 系列 | distanceRowing |
| paddleSports | distancePaddleSports |
| skatingSports | distanceSkatingSports |
| crossCountrySkiing | distanceCrossCountrySkiing |
| downhillSkiing | distanceDownhillSnowSports |
| wheelchairRunPace / wheelchairWalkPace | distanceWheelchair |
| 其余无距离语义的类型 | 不处理 |

以配置表而非硬编码分支实现，便于后续扩展新的运动类型。

### 2. 判重策略：区间重叠而非精确匹配

不能仅按"起止时间完全一致"判断是否已存在对应距离数据，原因：

- 其他来源（如 Apple Watch 自动记录）写入的距离数据，时间区间可能与训练记录整体区间不完全对齐（例如自动暂停场景下，只覆盖运动中的片段）
- 本 App 补写的数据是严格按训练记录的 `startDate`/`endDate` 写入的

因此判重逻辑为：查询对应距离类型下，是否存在满足 `sample.startDate < workout.endDate && sample.endDate > workout.startDate` 的记录。只要存在重叠记录（无论来源是本 App 还是其他 App），即判定为"已有距离数据"，跳过写入，不覆盖。

### 3. 写入内容

若训练记录对应距离类型没有统计值（`statistics(for:)` 返回 `nil`，或 `sumQuantity()` 取不到值），说明没有可搬运的数据源，直接跳过，不写入。

否则写入内容如下——新写入的 `HKQuantitySample`：

- 类型：按映射表确定
- 数值：训练记录 `statistics(for:)` 得到的 `sumQuantity()`
- 时间区间：与训练记录的 `startDate`/`endDate` 一致
- Metadata：附加自定义 key，记录来源训练的 `UUID`，用于追溯；同时加上 `HKMetadataKeyWasUserEntered: false`，标记这条数据是程序自动生成、不是用户手动录入

### 4. 本地记录与撤销

写入成功后，在本地持久化一条记录（技术选型：SwiftData）。具体字段以 `Sources/Models/SyncRecord.swift` 定义为准，不在本文档逐一列出、以免后续字段调整时文档跟着漂移；核心思路是记录来源训练 UUID、写入数据的 UUID、距离类型、数值、时间区间和写入时间，撤销和过期判断都靠这些字段驱动。

撤销操作：用 `HKQuery.predicateForObject(with: writtenSampleUUID)` 构造谓词，调用 `HKHealthStore.deleteObjects(of:predicate:)` 一步完成"查找+删除"，通过返回的删除数量判断结果——大于 0 即正常删除成功；等于 0 说明对应数据已被用户在健康 App 中手动删除、本地记录处于"悬空"状态，跳过删除、直接清理本地记录（对应 PRD 功能需求4），不需要"先查询是否存在、再决定要不要调用删除"这种两步流程。撤销后该训练在下次扫描时会因判重逻辑未命中而被重新识别为待补全。

界面提供"已写入记录"列表，支持单条撤销与批量撤销。

本地记录与 App 安装绑定，卸载重装会导致本地记录丢失；已写入健康 App 的数据不受影响但无法再通过本 App 撤销。本版本不设计基于 metadata 反查重建本地记录的恢复机制，metadata 仅用于追溯写入来源，视为已知限制（对应 PRD"已知限制"章节）。

### 5. 触发链路

- **后台自动**：对 `HKObjectType.workoutType()` 建立 `HKObserverQuery`，并调用 `enableBackgroundDelivery(for:frequency:.immediate)` 开启后台推送。新训练写入健康 App 后，系统唤醒本 App 执行补全逻辑。需在 Info.plist 中启用 HealthKit 后台模式（Background Modes）。
- **手动批量**：App 内提供"扫描历史"入口，遍历历史训练记录，对满足条件（有统计值、无重叠数据）的训练执行补全。

### 6. 权限范围

- Read：`HKObjectType.workoutType()`，以及映射表中涉及的全部距离类型
- Write：映射表中涉及的全部距离类型

不申请与本功能无关的其他 HealthKit 权限。

## 已知风险与后续关注点

- **后台唤醒时机不保证实时**：`enableBackgroundDelivery` 的 `.immediate` 频率仍受 iOS 系统调度影响，可能有延迟，需结合手动扫描作为补充，避免用户长期认为"没生效"
- **训练数据后续更新**：若源 App 后续对同一条训练记录的统计值进行了修正（如 GPS 数据重新处理），本方案按"不覆盖"原则，一旦补写过便不会再更新。对应的界面提示需求见 PRD 功能需求6"过期提示"；技术上可通过比较训练记录当前 `statistics(for:)` 的值与本地记录中保存的 `value` 是否一致，判断是否需要标记为"可能已过期"；若源训练记录本身已被删除、查不到对应训练，同样按"可能已过期"处理
- **多来源重复训练**：若同一时间段内存在多个来源各自记录的训练（如手表自动记录 + Zepp 记录），区间重叠判重可以避免重复计入，但也可能出现"本该属于本次训练的距离被判定为已存在从而跳过"的边界情况，后续可观察实际数据再决定是否需要更精细的判重规则
